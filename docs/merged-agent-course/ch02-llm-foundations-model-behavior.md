# 第 2 章：大语言模型基础与模型行为

> 本章目标：建立一套足以指导 Agent 工程的 LLM 心智模型。读完后，你应该能从自回归生成、注意力、分词、上下文和采样解释模型的常见行为，并知道哪些可靠性问题必须交给 Harness、工具和验证系统解决。

## 2.1 学习目标与边界

本章回答一个基础问题：**Agent 的“决策核心”为什么既强大又不可靠？**

你将理解：

- 语言模型如何把文本变成 Token，并逐 Token 生成输出。
- Transformer、自注意力和 Decoder-Only 架构与 Agent 行为有什么关系。
- 预训练、指令调优和对齐分别改变了什么，没有改变什么。
- 上下文、消息角色、采样参数和输出预算如何共同影响一次调用。
- 幻觉、指令漂移、位置敏感、随机性和“会说不会做”从何而来。
- 为什么 Agent 必须用外部观察、工具、状态和验证补齐模型边界。

本章不展开模型训练工程、分布式训练、微调配方，也不比较某一时刻的模型榜单。Prompt 的系统化设计放在第 4 章；Provider、路由与调用可靠性放在第 5 章；上下文压缩与会话状态放在第 6 章。

## 2.2 从概率语言模型到生成式模型

语言模型学习的是一个序列的概率。对 Token 序列 $x_1, x_2, \ldots, x_n$，链式法则把联合概率拆成：

$$
P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_{<t})
$$

早期 N-gram 只查看有限长度的前文；RNN 和 LSTM 用循环状态承载历史，但顺序计算限制了并行训练和长距离依赖。Transformer 用注意力在一个序列内直接建立位置间关系，使大规模并行训练成为可能。

现代通用生成模型多采用 Decoder-Only Transformer。训练时，因果掩码禁止当前位置查看未来 Token；推理时，模型依据已有前缀预测下一个 Token，再把新 Token 追加到前缀，重复执行：

```text
输入前缀
  -> 计算下一个 Token 的 logits
  -> 转换为概率分布
  -> 按解码策略选择 Token
  -> 追加到前缀
  -> 命中停止条件或预算后结束
```

这个机制带来一个极重要的工程结论：

**模型首先是一个条件生成器，不是事实数据库、事务处理器或形式化证明器。**

它可以在训练中学到大量知识和策略，也可以表现出规划、代码生成和工具选择能力，但每一步仍是依据当前可见前缀生成后续内容。事实性、执行权限、外部状态和“任务真的完成了没有”都不是自回归目标自动保证的属性。

## 2.3 Transformer：Agent 开发者需要理解到哪里

### 2.3.1 Token、向量与位置信息

模型不直接读取字符或“词义”。Tokenizer 先把文本编码成 Token ID，再映射为向量。子词分词在词表规模与表达能力之间折中：常见片段可以是一个 Token，罕见词、中文、代码符号或空白可能被拆成多个 Token。

这会产生几类工程后果：

- 字符数不等于 Token 数，中文、代码、JSON 和长标识符的成本不同。
- Schema、工具描述、历史消息和工具结果都占上下文预算。
- 截断发生在 Token 边界，可能切断 JSON、代码块或工具参数。
- 同一段语义换一种格式，Token 数和模型可解析性可能明显变化。

位置编码或位置表示为模型提供 Token 顺序信号。若注意力层完全没有任何位置表示，它本身对输入排列缺少区分依据；至于模型能否理解“先读后改”和“先改后读”，还取决于位置机制、训练数据和后续网络如何共同利用这些信号，不能只归因于某一种位置编码实现。

### 2.3.2 自注意力不是无限注意力

缩放点积注意力可写为：

$$
\operatorname{Attention}(Q,K,V)=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

对 Agent 开发者，关键不是手算矩阵，而是理解三件事：

1. 每个位置会根据当前表示从其他可见位置聚合信息。
2. 多头注意力允许模型同时捕捉不同关系，但不保证抓住工程上最重要的约束。
3. 上下文窗口是“可访问上限”，不是“所有内容被同等可靠利用”的保证。

长 Prompt 中，重复、冲突和低价值内容会争夺模型的有限计算与注意力。关键信息位于不同位置时，利用率也可能变化。因此，把整个仓库、全部工具和所有历史一次性塞进上下文，并不等于模型“掌握了全局”。

### 2.3.3 前馈层、残差与规模

注意力负责跨位置聚合，逐位置前馈网络负责变换表示；残差连接和归一化让深层网络能够稳定训练。模型规模、训练数据和计算量增加，通常会平滑降低训练损失并扩大能力范围，但工程上不能把“更大”简化为“每个任务都更可靠”。

模型还受训练数据质量、后训练目标、上下文长度、推理预算、工具训练和具体任务分布影响。所谓“涌现”有时是能力真正跨过阈值，有时也来自离散评分把连续改进显示成突然跳变。选型必须看目标任务评测，而不是只看参数规模或综合榜单。

## 2.4 预训练、指令调优与对齐

### 2.4.1 预训练获得的是模式与能力

预训练让模型从海量数据中学习语言、代码、事实关联和任务模式。它能压缩并重组训练分布中的规律，却不会为每个陈述附带可查询的来源，也没有一个与现实世界实时同步的数据库。

因此，“模型知道某事”更准确地说是：给定某种上下文时，模型有较高概率生成相关、正确的内容。这个概率会随措辞、上下文冲突、知识时效和采样过程变化。

### 2.4.2 指令调优获得的是交互习惯

基础模型更像续写器。指令调优通过“指令—回答”数据，让模型更习惯识别请求、遵守角色和按格式作答。偏好优化、安全训练和工具调用训练进一步塑造默认行为，例如更愿意解释、拒绝危险请求或输出结构化工具参数。

但后训练没有把模型变成确定性程序：

- “倾向遵守”不等于“必然遵守”。
- 安全拒绝可能误伤正常任务，也可能在复杂上下文中失效。
- 不同模型版本的默认主动性、详细程度和工具偏好会变化。
- 模型能生成一个看似合法的工具调用，不代表参数满足业务约束。

Prompt 负责引导概率，Runtime 和代码负责强制不变量。

### 2.4.3 消息角色最终仍会被序列化

API 暴露 `system`、`developer`、`user`、`assistant`、`tool` 等角色，是为了表达来源和优先级。Provider 会把这些消息按模型协议编码后送入模型。角色不是普通文本标签，但也不能被误解为数据库权限系统。

一条低优先级消息中的恶意指令可能与高优先级规则竞争；模型读取网页、邮件或文件时，也可能把其中的文本误当成行动指令。这就是 Prompt Injection 的根源之一。真正的安全边界仍需要工具白名单、权限判断、数据隔离和沙箱。

## 2.5 生成机制如何塑造模型行为

### 2.5.1 logits、Softmax 与采样

模型为候选 Token 产生 logits，经 Softmax 得到概率。温度 $T$ 会改变分布形状：

$$
p_i(T)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}}
$$

低温度通常让分布更集中，高温度增加多样性。Top-k 保留概率最高的固定数量候选；Top-p 保留累计概率达到阈值的最小候选集合。

但不要把 `temperature=0` 理解成跨时间、跨 Provider 的绝对确定性。并行计算、服务端实现、模型版本、隐藏系统指令和工具返回差异，都可能改变最终输出。对可靠 Agent，确定性来自约束、工具和测试，而不是单个采样参数。

### 2.5.2 输出预算也是行为约束

模型输出可能因停止序列、自然停止、工具调用、内容过滤或 `max_output_tokens` 而结束。截断不只是“回答短了”：它可能留下半个工具参数、未闭合代码块或尚未执行的计划。

所以 Runtime 必须区分：

- 正常完成。
- 请求调用工具。
- 输出预算耗尽。
- 安全或策略中止。
- 流式连接中断。
- Provider 返回错误。

把所有停止都解释成“模型做完了”，是 Agent Loop 最早也最危险的简化之一。

### 2.5.3 推理文本不等于可验证推理

Chain-of-Thought、reasoning token 或“逐步思考”可以提升某些复杂任务表现，但一段流畅的解释仍可能是事后合理化、遗漏步骤或计算错误。内部推理是否可见、是否应保存，还受 Provider 协议与安全策略约束。

工程上更可靠的做法是要求**可验证中间产物**：计划、查询结果、计算器输出、测试结果、引用和状态变更记录。验证对象应是环境证据，而不是模型声称自己“认真检查过”。

## 2.6 六类核心模型行为

### 2.6.1 上下文依赖

模型没有脱离当前请求的稳定“工作记忆”。它的行为取决于本次可见的消息、工具定义和协议项。同一个问题放入不同历史、不同项目规则或不同工具集合，答案可能不同。

### 2.6.2 概率性与路径依赖

早期生成的一个 Token、一个错误假设或一次工具观察，会改变后续全部条件。长任务因此具有路径依赖：开始时的小偏差可能被后续自然语言不断强化。

### 2.6.3 模式补全倾向

模型擅长延续已有结构。示例能快速校准格式和行为，但错误示例、过时示例和不完整轨迹也会被模仿。Few-shot 的价值不是“越多越好”，而是给出少量、边界清晰、与目标分布匹配的示范。

### 2.6.4 迎合与过度自信

当证据不足时，模型仍可能生成一个听起来完整的答案；当用户暗示某个结论时，模型可能顺着前提继续补全。应允许模型表达“不确定”“未找到证据”和“需要工具核实”，并通过外部验证区分未知与错误。

### 2.6.5 指令竞争与注意力稀释

重复规则不一定增强服从。多份近义或冲突指令会增加解释空间；过长工具列表会降低选择准确率；动态噪声放在 Prompt 前部还会破坏缓存。Prompt Runtime 的任务之一，就是只组装本轮必要且一致的控制信息。

### 2.6.6 能力与授权分离

模型可能有能力构造删除命令、发送邮件或修改生产配置，但“能生成动作”不等于“被授权执行动作”。Agent 必须把能力、可见性、授权和执行四层分开：

```text
模型能力：能否理解并提出动作
工具可见性：本轮是否向模型暴露该工具
权限决策：当前用户与场景是否允许
执行环境：动作真正能影响哪些资源
```

## 2.7 幻觉不是单一故障

“幻觉”至少包含四类不同问题：

| 类型 | 表现 | 更合适的缓解方式 |
| --- | --- | --- |
| 事实性错误 | 编造实体、日期、引用 | 检索、权威来源、交叉核对 |
| 上下文不忠实 | 摘要与给定材料矛盾 | 引用定位、覆盖率检查、结构化抽取 |
| 推理错误 | 中间步骤遗漏或计算错误 | 计算工具、计划、测试、独立验证 |
| 行动幻觉 | 声称已执行但没有环境证据 | 工具回执、状态读取、验收契约 |

RAG 只直接缓解知识获取问题；它不能自动修复错误检索、错误推理或虚假完成声明。工具调用也只把模型连接到环境，工具结果仍可能过期、截断、被误读或携带注入内容。

可靠性来自完整链路：**取证、执行、观察、验证、停止**。

## 2.8 从聊天模型到 Agent 决策核心

普通聊天把一次模型输出当作最终产品。Agent 把模型输出当作下一步控制信号之一：

```text
自然语言请求
  -> Prompt Runtime 组装有效上下文
  -> Model Runtime 调用模型
  -> 文本 / 工具调用 / 状态信号
  -> Harness 校验并执行
  -> 环境观察写回上下文
  -> 模型基于新证据继续决策
```

这种设计利用了模型的强项：理解模糊意图、在开放空间中提出下一步、把非结构化观察综合成策略。同时把弱项交给确定性系统：Schema 验证、权限、计算、持久状态、事务、超时、成本和验收。

判断某个职责该放在哪里，可以用一条简单规则：

- 需要语义判断、开放探索或自然语言综合时，让模型参与。
- 需要硬约束、精确计算、权限保证或可重复结果时，用代码和工具。

## 2.9 最小实现：看见自回归生成

下面的伪代码省略神经网络内部计算，只保留生成机制：

```python
def generate(model, tokenizer, prompt, max_new_tokens, temperature=0.2):
    token_ids = tokenizer.encode(prompt)

    for _ in range(max_new_tokens):
        logits = model.forward(token_ids)[-1]
        probs = softmax(logits / max(temperature, 1e-6))
        next_id = sample(probs)

        if next_id in tokenizer.stop_token_ids:
            break

        token_ids.append(next_id)

    return tokenizer.decode(token_ids)
```

把它放进 Agent 语境，还需在模型前后增加协议：

```python
request = {
    "messages": serialize_roles(messages),
    "tools": tool_schemas,
    "max_output_tokens": output_budget,
}

response = model_runtime.generate(request)
event = parse_response(response)  # text, tool_call, usage, stop_reason...
```

第一个函数解释“模型如何生成”；第二段解释“Agent 如何消费生成”。后面三章分别补上循环、Prompt Runtime 和 Model Runtime。

## 2.10 生产约束

### Token 与延迟

输入越长，首 Token 延迟、成本和上下文管理压力通常越高；输出越长，总延迟和失败暴露面越大。需要分别预算静态 Prompt、动态上下文、工具 Schema、历史消息、工具结果和输出。

### 数据与时效

训练知识有截止时间，API 模型还可能在不通知应用代码的情况下升级别名。涉及最新事实、法规、价格或远端状态时，必须查询实时来源。敏感数据进入第三方模型前要符合数据治理策略。

### 模型差异

“支持文本”远远不够。Agent 还依赖工具调用、结构化输出、上下文窗口、流式协议、图像输入、推理项续传和错误语义。能力必须由 Runtime 声明并通过契约测试确认。

### 不可观测内部状态

不要把模型解释当成内部机制的完整记录，也不要把不可见推理当成审计日志。生产审计应记录输入版本、工具轨迹、环境证据、输出、用量和停止原因。

## 2.11 常见失败模式

**把模型当搜索引擎。** 对时效和精确出处没有外部检索，得到流畅但过时的答案。

**把低温度当正确性保证。** 输出更稳定，但稳定地产生错误同样可能发生。

**把上下文窗口当有效记忆。** 内容能放进去，不代表关键约束一定被可靠使用。

**把推理长度当推理质量。** 更长的解释可能增加错误链条和成本，没有外部验证就无法判定。

**把工具调用当执行成功。** 模型提出动作后，仍可能被 Schema、权限、网络或业务规则拒绝。

**把模型升级当无损替换。** 默认风格、主动性、工具选择和参数支持变化，旧 Prompt 补丁可能失效或反向干扰。

**把所有异常叫幻觉。** 不区分知识、推理、协议与执行错误，就无法选择正确修复层。

## 2.12 测试与验收

本章知识应落到一个“模型行为画像”评测集，而不是停在概念问答。

| 测试组 | 示例 | 验收信号 |
| --- | --- | --- |
| 重复性 | 同一请求运行多次 | 记录结果分布，不要求逐字一致 |
| 上下文敏感性 | 改变规则位置或加入冲突信息 | 识别优先级与退化点 |
| 长上下文 | 关键约束放在开头、中间、结尾 | 比较约束遵守率 |
| 事实性 | 已知答案、过时知识、需实时查询 | 正确使用“不确定/检索” |
| 结构化输出 | JSON、工具参数、截断场景 | Schema 通过率与修复率 |
| 指令注入 | 文档中包含恶意行动指令 | 不把数据当高优先级命令 |
| 行动诚实性 | 无执行工具却要求确认完成 | 不虚构工具回执 |

验收时至少记录：模型版本、参数、Prompt 版本、工具集合、成功率、格式通过率、Token、延迟和失败分类。只保留最终回答会丢掉最有价值的诊断证据。

## 2.13 系统地图

```text
训练与后训练
  -> 获得语言、知识、推理和指令遵循倾向

Tokenizer + 消息协议
  -> 把角色、文本、工具 Schema 编码成 Token 序列

Decoder-Only Transformer
  -> 基于可见前缀计算下一 Token 分布

采样与停止规则
  -> 生成文本、工具调用或其他协议项

Harness
  -> 校验、授权、执行、记录、验证、停止

外部环境
  -> 返回事实与状态，进入下一轮条件上下文
```

## 2.14 共同结论

1. LLM 的基本机制是条件概率生成，强能力不等于确定性保证。
2. 上下文是一次调用的工作空间，不是自动可靠的数据库或长期记忆。
3. Prompt、示例和采样参数能改变行为分布，不能强制安全与事实正确。
4. 工具把模型连接到真实环境，但只有验证链路能证明任务完成。
5. Agent 工程的核心不是消灭模型的不确定性，而是让不确定决策被确定性边界约束、被环境证据纠正、被评测持续观察。
