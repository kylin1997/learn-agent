# 第 1 章：Agent、智能体历史与 Harness

> 本章目标：建立全书共用的概念地基。读完后，你应该能从任务环境而不是产品标签判断一个系统是否具有 Agent 特征；能说明传统智能体如何演进为 LLM Agent；能区分 Chatbot、Workflow 与 Agent；也能解释模型和 Harness 分别承担什么责任。

## 1.1 为什么“Agent”越来越难定义

“Agent”至少在三个层面被使用。

第一层是人工智能中的**智能体**：它感知环境，根据目标选择行动，并用行动改变环境。恒温器、自动驾驶系统、游戏 AI 和软件助手都可以放进这个宽泛定义。

第二层是以大语言模型为决策核心的 **LLM Agent**：模型理解自然语言目标，读取当前上下文，选择工具，再根据工具反馈调整下一步行动。

第三层是用户实际接触的 **Agent 产品**：它除了模型，还包含工具、权限、会话、记忆、运行时、界面、日志、恢复和评测。Claude Code、Hermes 一类系统属于这一层。

如果把三个层面混在一起，就会产生两种相反的误解：一种把任何接入 LLM 的流程都叫 Agent；另一种认为 Agent 只是模型，外部工程无关紧要。本章采用两组互补的定义：

```text
通用智能体 = 在任务环境中，根据观察和内部状态选择行动，以推进目标的系统

LLM Agent 产品 = Model + Harness
```

第一组定义解释“什么是智能体”，第二组解释“怎样把 LLM 的能力做成可工作的产品”。`Model + Harness` 是本课程采用的工程模型，不是对全部智能体研究的唯一学术定义。

## 1.2 智能体的通用结构

### 1.2.1 七个核心审查问题

理解一个智能体时，先回答七个问题。

| 要素 | 要回答的问题 | 编码 Agent 示例 |
| --- | --- | --- |
| 目标 Goal | 系统要把世界推向什么状态？ | 功能完成、测试通过、变更可审查 |
| 环境 Environment | 它在哪个世界中行动？ | 代码库、终端、版本控制和外部服务 |
| 感知 Perception | 它能看到什么？ | 用户指令、文件内容、测试输出、Git diff |
| 状态 State | 它如何表示当前世界和任务进度？ | 消息历史、计划、工作树状态、任务记录 |
| 决策 Policy | 它如何选择下一步？ | LLM、规则、搜索算法或学习到的策略 |
| 行动 Action | 它能改变什么？ | 编辑文件、执行命令、调用 API、回复用户 |
| 评价 Evaluation | 怎样判断行动有用、任务完成或风险过高？ | 测试、静态检查、验收标准、人工审批 |

在时间步 `t`，可以把决策抽象为：

```text
action_t = policy(goal, observation_1..t, internal_state_t, constraints)
```

环境执行行动后产生新状态和新观察，智能体再做下一次决策。第 3 章会展开这个循环的代码结构；本章只强调一个事实：**智能体的决策离不开它能看到的环境、保留的状态和允许执行的行动。**

### 1.2.2 自主性不是开关

自主性指系统能在多大程度上自行选择达成目标的路径。它不是“有或没有”的二元标签。

```text
低自主性                                                高自主性
文本补全 -> 单步工具建议 -> 人审批每一步 -> 自主选工具 -> 自主分解任务 -> 长期主动运行
```

自主性至少包含四种决策权：

1. **路径决策权**：下一步做什么，由代码预先规定还是由模型运行时选择。
2. **行动决策权**：系统能否直接改变外部状态，还是只能提出建议。
3. **停止决策权**：系统能否判断目标完成、无法继续或需要升级给人。
4. **时间决策权**：系统只能在用户发起时工作，还是能被事件、定时器或长期目标唤醒。

同一个产品也可能在不同操作上采用不同自主性。读取公开文档可以自动执行，转账则要求人确认。成熟设计不会追求“自主性最大化”，而会根据可逆性、损失上限和验证能力分配决策权。

## 1.3 先定义任务环境：PEAS

传统 AI 使用 PEAS 描述任务环境：

- **P, Performance measure**：性能度量，什么结果算好。
- **E, Environment**：环境，智能体面对的外部世界。
- **A, Actuators**：执行器，智能体用什么方式改变环境。
- **S, Sensors**：传感器，智能体通过什么渠道观察环境。

以“修复代码缺陷”为例：

| PEAS | 具体内容 |
| --- | --- |
| P | 缺陷消失、测试通过、改动范围合理、没有引入安全问题 |
| E | 仓库文件、依赖、编译器、测试系统、Git 历史、CI |
| A | 文件编辑、命令执行、依赖查询、提交或创建补丁 |
| S | 用户描述、代码搜索结果、诊断信息、测试日志、diff |

PEAS 的价值在于迫使你先定义“工作世界”。如果性能度量模糊，Agent 会把“有输出”误当成“完成”；如果传感器看不到测试失败，模型再强也无法根据失败修正；如果执行器只有文本回复，系统就仍然需要人代替它行动。

### 1.3.1 环境属性会决定架构

任务环境可以从多个维度分析。

| 环境属性 | 含义 | 对 Agent 工程的影响 |
| --- | --- | --- |
| 完全 / 部分可观察 | 能否获得决策所需的全部状态 | 部分可观察环境需要搜索、记忆、状态估计和澄清 |
| 确定 / 随机 | 同一行动是否总产生同一结果 | 随机环境需要重试、置信度、抽样和风险控制 |
| 单步 / 序贯 | 当前行动是否影响后续决策 | 序贯任务需要计划、轨迹和中间状态 |
| 静态 / 动态 | 决策期间环境是否继续变化 | 动态环境需要超时、重读、版本检查和冲突处理 |
| 单 Agent / 多 Agent | 是否存在其他行动者 | 多方协作需要身份、通信、并发和一致性机制 |
| 离散 / 连续 | 状态和行动空间是否可枚举 | 连续控制通常需要不同于文本工具调用的策略 |

软件 Agent 常处在“部分可观察、序贯、动态、多行动者”的环境中。文件可能被别人修改，API 数据可能过期，前一步编辑会改变后续测试结果。很多所谓的模型问题，其实是环境建模失败：观察不完整、反馈太晚或状态已经过期。

## 1.4 传统智能体并没有过时

现代 LLM Agent 继承了传统智能体的基本问题，只是更换了决策核心和知识获取方式。

### 1.4.1 五类经典结构

**简单反射智能体**根据当前观察执行条件动作规则。例如“温度高于阈值就打开制冷”。它快速、可预测，但没有历史状态。

**基于模型的反射智能体**维护内部世界状态，用来补足当前观察看不到的信息。它开始具备最小意义上的记忆。

**基于目标的智能体**比较多个未来状态，选择能推进目标的行动。路径规划、任务分解和搜索都属于这个方向。

**基于效用的智能体**不只问“能否达成”，还比较成本、时间、风险和收益。现实任务通常存在冲突目标，因此生产 Agent 迟早要面对效用权衡。

**学习型智能体**根据经验更新策略。学习不是与前四类并列的单一结构，它可以改进反射规则、世界模型、目标规划或效用估计。

这五类结构今天仍然共存。权限规则可以是反射式的，任务规划可以是目标式的，模型路由可以按效用权衡，技能演进则属于学习机制。LLM Agent 并没有消灭规则和搜索，而是把它们重新组合在一个更通用的决策系统里。

### 1.4.2 反应与规划的组合

反应式系统响应快，适合超时处理、危险拦截和简单路由。规划式系统会先比较行动序列，适合复杂任务，但成本更高，而且计划可能在动态环境中迅速失效。

现代 Agent 多采用混合结构：

```text
高层：目标分解、计划、预算和停止条件
低层：读取当前观察，选择下一步动作，立即吸收反馈
硬边界：权限、超时、资源限制和安全规则
```

模型负责需要语义判断的部分，确定性代码负责必须稳定成立的约束。这条分工会贯穿全书。

## 1.5 一条问题驱动的智能体简史

智能体研究由多条路线并行推进：符号推理、分布式协作、神经网络和强化学习长期共存，也相互吸收。下面按它们主要解决的问题组织简史，不把它们写成严格的前后继承关系。

### 1.5.1 符号、逻辑与专家系统

早期人工智能把知识写成符号和规则，再由推理机执行正向链或反向链。专家系统证明了明确知识和逻辑推理可以在封闭领域产生高质量决策。

它的瓶颈是知识获取和脆弱性。工程师需要手工整理大量规则，真实世界的例外又会让规则数量快速膨胀。系统能解释规则，却难以从原始数据中学习，也很难迁移到新领域。

### 1.5.2 从单一推理器到协作结构

分布式 AI 和多智能体研究把复杂智能拆给多个相互作用的单元。明斯基的“心智社会”提供了一个理解视角：复杂能力可以来自许多局部能力的协同，而不必假设一个无所不能的中央模块。

今天可以借这个视角理解子 Agent、专家路由和多 Agent 团队，但两者不构成直接的技术继承关系。拆分也不会自动产生更强能力；通信成本、目标冲突和结果汇总始终存在，第 16 章会专门讨论这些问题。

### 1.5.3 联结主义与从数据中学习

神经网络把知识分布在参数中，通过数据和优化算法学习表示。深度学习显著提升了图像、语音和文本感知能力，减少了手工编写特征和规则的需求。

这种方法解决了“如何从大量样本中获得模式”的问题，但参数中的知识难以直接检查，模型也可能在分布外输入上失效。可解释规则让位给统计泛化后，验证和治理变得更重要。

### 1.5.4 强化学习与序贯决策

强化学习让智能体通过状态、行动和奖励学习策略，目标是最大化长期回报。它把“看懂输入”推进到“在环境反馈中学会行动”。游戏智能体展示了模型可以从大量交互轨迹中学到复杂策略。

强化学习依赖明确的环境和奖励，大规模真实交互又昂贵且危险。奖励设计不完整时，智能体可能优化指标却偏离真实目标。这个问题后来以新的形式出现在 LLM Agent 的评测和自进化中。

### 1.5.5 预训练模型与自然语言接口

大规模预训练让一个模型在使用前就拥有广泛的语言模式、知识和任务先验。人们可以用自然语言描述新任务，通过上下文提供示例和约束，而不必为每个任务重新训练一个专用模型。

这一步改变了 Agent 的构建成本。过去，开发者主要编写规则或训练专用策略；现在，开发者可以把通用模型接入具体环境，让模型在运行时解释目标、选择动作并生成结构化调用。

### 1.5.6 LLM Agent：几条传统路线重新汇合

LLM Agent 不是单纯的联结主义系统。它的模型来自神经网络训练，却会处理符号化的计划、JSON 参数、程序代码和工具契约；它也可能使用规则权限、搜索算法、数据库和强化学习得到的行为偏好。

因此，更准确的历史结论是：现代 Agent 把学习到的通用模型放在决策中心，再用符号接口、外部工具、状态系统和反馈机制约束其行动。历史中的规则、规划、学习和协作没有消失，它们进入了 Harness 的不同位置。

## 1.6 从传统智能体到 LLM Agent，真正改变了什么

下表比较的是规则式或任务专用 Agent 与典型 LLM Agent，目的是说明工程重心的迁移，并不覆盖强化学习、概率规划等全部传统路线。

| 维度 | 规则式或任务专用 Agent | 典型 LLM Agent |
| --- | --- | --- |
| 决策核心 | 人工规则、搜索算法或专用策略 | 预训练语言模型与必要的确定性策略 |
| 知识来源 | 显式知识库、任务数据、环境交互 | 预训练知识、上下文、检索和工具观察 |
| 任务接口 | 结构化状态和固定动作空间 | 自然语言目标加结构化工具接口 |
| 泛化方式 | 在预设领域内工作 | 可用指令和示例适配大量新任务 |
| 可预测性 | 边界明确，行为较稳定 | 概率性强，对上下文和工具描述敏感 |
| 主要瓶颈 | 规则规模、知识获取、任务迁移 | 可靠性、状态、权限、验证和成本 |

LLM 带来的最大变化，是让**目标、约束和行动接口可以用语言描述**。用户可以说“修复登录失败并补测试”，模型再依靠训练所得的策略把它解释成一组待验证的行动，开发者不必预先穷举全部路径。

但自然语言的灵活性也带来歧义。模型可能误解目标、选择错误工具、相信不可靠观察，或者在看似合理时过早停止。LLM 提高了系统面对开放任务的上限，也扩大了 Harness 需要治理的行为空间。

## 1.7 Chatbot、Workflow 与 Agent

Anthropic 在 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 中区分了两类 agentic system：Workflow 由预定义代码路径编排模型和工具，Agent 则让模型动态决定过程和工具使用。这个区分比“是否使用 LLM”更有用。

| 系统形态 | 谁决定路径 | 是否改变外部状态 | 是否根据反馈改路 | 适合任务 |
| --- | --- | --- | --- | --- |
| Chatbot | 单次提示或对话协议 | 通常不改变 | 主要生成回复 | 问答、解释、内容生成 |
| LLM Workflow | 开发者预先定义 | 可以 | 在预设分支内 | 稳定流程、批处理、审批链 |
| Agent | 模型在运行时决定 | 通常可以 | 可以生成未预写的下一步 | 路径开放、需要探索的任务 |
| Hybrid | 代码规定阶段，模型决定局部路径 | 可以 | 在授权区域内 | 大多数生产系统 |

### 1.7.1 Agent 是一条连续谱

一个固定的“提取字段 → 查询数据库 → 生成邮件”流程，即使三个节点都调用 LLM，仍然是 Workflow。一个系统如果让模型根据数据库结果决定继续搜索、向用户澄清还是终止，就开始具有 Agent 特征。

判定重点是**运行时决策权**：

- 开发者是否提前写死行动顺序？
- 模型能否根据新观察选择不同工具？
- 系统能否形成开发者没有逐步列出的行动路径？
- 外部反馈能否改变后续决策？

这也说明 Workflow 和 Agent 可以嵌套。确定性工作流可以调用 Agent 处理开放步骤，Agent 也可以把稳定子任务交给工作流执行。

### 1.7.2 什么时候不该使用 Agent

以下任务优先使用确定性代码或 Workflow：

- 步骤固定，输入输出格式稳定。
- 错误代价高，但缺少可靠验证器。
- 延迟和成本必须严格可预测。
- 规则足够简单，模型不会增加有效判断。
- 合规要求禁止模型自行选择行动路径。

Agent 适合路径难以穷举、反馈会改变下一步、任务需要语义判断和多轮探索的场景。工程目标不是把更多流程改名为 Agent，而是把模型决策放在确实需要判断力的位置。

## 1.8 Model 与 Harness

`learn-claude-code` 提出一个鲜明观点：感知、推理和行动选择的通用能力来自模型训练，大多数应用开发者实际构建的是 Harness。第 11 个来源用 `Agent = LLM + 上下文 + 工具` 表达相近主张；本课程把状态、权限、反馈、恢复和评测也纳入 Harness，因此采用覆盖面更完整的 `Agent Product = Model + Harness`。这个观点能纠正“堆更多节点就能编码出智能”的误区，但需要加上工程边界。

### 1.8.1 模型负责什么

模型提供学习到的先验和概率性决策能力：

- 理解自然语言目标和约束。
- 从不完整信息中提出假设。
- 分解开放任务并选择候选行动。
- 解释工具观察，调整后续路径。
- 在新任务上复用训练中获得的模式。

模型不会天然知道当前文件、实时价格、用户权限或任务是否通过测试。它也不能只靠生成文本可靠地改变外部世界。

### 1.8.2 Harness 负责什么

Harness 是模型在某个任务环境中的工作条件。这里的来源分工并不相同：`hello-agents` 提供传统定义与历史主线，`learn-claude-code` 和 Alice 提供 Harness 工程主线，Hermes、OpenClaw、Claude Code 等项目用于检验这些概念在真实系统中的落点。本课程据此综合出：

```text
Harness = Interaction Contract
        + Prompt / Context / Knowledge
        + Observation / Tools / Action Interfaces
        + Session / State / Memory
        + Permissions / Sandbox / Human Approval
        + Runtime / Routing / Recovery
        + Tracing / Evaluation / Feedback
```

Harness 决定模型能看到什么、能做什么、如何知道结果、哪些行为会被拒绝、失败后怎样恢复。它不会把弱模型变成无所不能的决策者，但会决定模型能力能否在真实环境中稳定表达。

因此，`Agent Product = Model + Harness` 不是简单加法。两者必须匹配：工具描述要适合模型理解，上下文要符合窗口限制，验证器要能检查行动结果，权限要覆盖模型可能选择的路径。

### 1.8.3 软约束与硬约束

| 约束类型 | 典型机制 | 适合内容 |
| --- | --- | --- |
| 软约束 | System Prompt、示例、Skill、计划模板 | 风格、工作方法、优先级、协作习惯 |
| 硬约束 | 代码校验、权限规则、沙箱、预算、类型系统 | 文件边界、金额上限、危险操作、资源限制 |

“请不要删除生产数据”不能只写在 Prompt 中。模型可能误解、忽略或被外部内容诱导。损失不可接受的边界必须由模型之外的代码执行。

### 1.8.4 工具与内部服务

Alice 方法论强调工具与内部服务的结构隔离：

- **工具**对模型可见，表示模型可以主动选择的行动，例如读文件、运行测试或查询数据库。
- **内部服务**由 Harness 自己使用，例如日志写入、任务排队、超时控制、会话保存和密钥轮换。

把所有能力都暴露成工具，会增加选择噪声，还可能让模型修改本应由运行时控制的内部状态。判断标准很直接：这个动作是否需要模型根据任务语义来选择？如果不需要，就让确定性服务处理。

### 1.8.5 工程范式的演进弧

`ai-agent-book` 把 LLM 应用工程组织成一条层层包含的演进弧：

```text
软件工程 ⊃ 提示工程 ⊃ 上下文工程 ⊃ Harness 工程 ⊃ Loop 工程
```

每一层都包含前一层，并接管它解决不了的问题：软件工程提供系统与接口；提示工程把指令当作设计对象；上下文工程管理模型在每一步能看到什么；Harness 工程再加上工具、权限、验证与恢复；Loop 工程则关注跨任务、跨时间的持续运行与改进。

这个演进弧有实证支撑：LangChain 在 Terminal Bench 2.0 上仅通过改进 Harness（不改模型）就把通过率从 52.8% 提升到 66.5%。它印证了本章的核心判断：模型能力给定后，工程层的改进空间往往大于换更大的模型。

### 1.8.5 工程范式的演进弧

`ai-agent-book` 把 Agent 应用的工程实践组织成一条层层包含的演进弧线：

- **软件工程**是基础：传统的系统设计、架构、测试和部署实践。
- **提示工程**是第一波：通过优化输入给模型的自然语言指令提升输出质量。
- **上下文工程**是第二波：系统性地管理模型能看到的所有信息，包括系统指令、工具定义、对话历史和外部知识。
- **Harness 工程**是第三波：把视野从“模型能看到什么”扩展到“模型在什么样的系统中运行”，涵盖约束机制、验证手段、反馈循环和错误恢复等模型之外的全部基础设施。
- **Loop 工程**是最新一波：把视野从单次运行扩展到跨轮次的持续自主运转——谁来发现下一件该做的事、何时验证、何时才算真正完成。

这五个阶段不是替代关系，而是层层包含的：提示工程是上下文工程的子集，上下文工程是 Harness 工程的子集，Harness 工程是 Loop 工程的子集。每一层都在前一层的基础上扩展了工程师的关注范围。当各家模型的能力越来越接近、不再是决定性差异时，竞争优势就转移到模型之外的工程实践。一个直接例证是 LangChain 在 Terminal Bench 2.0（评估 Agent 在终端环境完成复杂任务能力的基准）上的实践：他们的 Coding Agent 成绩从 52.8% 提升到 66.5%，跃居排行榜前 5，改变的不是模型，而是 Harness——让 Agent 自动检查执行结果、检测是否陷入重复循环、优化思考策略等工程手段。

## 1.9 两层系统地图

第一层地图描述任何智能体都绕不开的闭环：目标和评价定义方向，环境产生观察，智能体根据状态选择行动，行动再改变环境。

第二层地图描述 LLM Agent 产品：用户或事件进入运行时，编排器组织 Model 与 Harness 的交互；Harness 向模型提供上下文、观察、工具、状态和权限，并用追踪与评测记录结果。

## 1.10 三个系统案例说明 Harness 如何随产品改变

### 1.10.1 编码 Agent

Claude Code 类系统面对的是本地代码环境。它的核心观察包括文件、诊断信息、Git diff 和测试输出；行动包括搜索、编辑和执行命令；主要风险是破坏工作树、泄露数据和执行危险命令。因此，它的 Harness 强调文件工具、终端、项目规则、权限审批、上下文压缩和可恢复的任务状态。

### 1.10.2 长期个人 Agent

Hermes 类系统把时间跨度从一次任务扩展到长期协作。除了工具和会话，它还需要持久记忆、技能沉淀、多入口、定时唤醒和后台复盘。产品定位改变后，Harness 的状态生命周期、身份边界和资源预算都会改变。

### 1.10.3 多渠道常驻 Agent

OpenClaw 和 `claw0` 展示了另一种增量路径：在 Agent 内核之外逐步增加渠道适配、Gateway、心跳、Cron、可靠投递、错误恢复和并发控制。这里的关键不是某个产品配置，而是**同一个决策内核需要一套常驻运行基础设施，才能从临时会话走向持续服务**。

三个案例使用不同的入口和状态周期，却共享同一原则：先定义任务环境，再为模型提供合适的观察、行动、边界和反馈。

## 1.11 从哪里开始设计一个 Agent

不要先选框架。先完成一页任务环境设计。

1. 写出目标状态和不可接受的结果。
2. 用 PEAS 列出性能度量、环境、执行器和传感器。
3. 标记环境中不可见、会变化或不确定的状态。
4. 区分确定性步骤和确实需要模型判断的步骤。
5. 为每个行动标注可逆性、损失上限和审批要求。
6. 为关键结果设计可执行的验证器。
7. 最后才决定模型、工具协议、框架和存储方式。

例如，“自动修复缺陷”不是充分的目标。更可执行的定义是：“在当前分支内定位导致指定失败测试的原因，做最小修改，使目标测试和相关回归测试通过；不得修改数据库迁移，不得提交代码；无法验证时输出证据并请求人工判断。”

这段定义已经给出了目标、范围、硬边界、验证方式和升级条件。模型选择反而是后面的决策。

## 1.12 常见误解

讨论误解之前，先给出 `ai-agent-book` 引用 Anthropic 经验总结的三条构建原则，它们正是下面多个误解的解法：

1. **保持简单**。从最简单的方案开始，只在确实必要时才增加复杂度。直接的 API 调用优于复杂的框架，清晰的代码优于聪明的抽象——每多一层抽象都会成为以后调试时新的盲区。
2. **保持透明**。明确显示 Agent 的规划步骤、执行日志和决策轨迹。这不只是为了调试方便，也是让用户建立信任的前提：黑箱里的错误一旦发生，外部观察者既无法定位也无法纠正。
3. **设计好工具接口（ACI，Agent-Computer Interface）**。从 Agent 视角而非程序员视角设计接口：工具命名和参数要直观，容易误用的地方要主动防呆。这种“用设计消除错误”的思路源自丰田生产体系，称为防呆（Poka-yoke）。模型与工具之间唯一的沟通通道就是接口本身，模糊的接口会被模型放大成系统性错误。

`ai-agent-book` 把构建有效 Agent 的经验总结为三原则：**保持简单**（能不用 Agent 就不用，从最简方案起步）、**保持透明**（让 Agent 展示计划、行动与理由，人能审查和纠正）、**设计好工具接口**。第三条即 ACI（Agent-Computer Interface）：工具是模型与计算机的交互界面，应当像对待 UX 一样打磨工具命名、参数与反馈，并用 Poka-yoke（防呆）设计让错误用法在接口层就被阻止。下面的误解大多源于违反这三条原则。

**误解一：接入 LLM 就是 Agent。** 只有当模型获得一定的路径决策权，并能根据环境反馈调整行动时，系统才具有明显的 Agent 特征。

**误解二：工具越多，Agent 越强。** 工具会扩大行动空间，也会增加选择难度和风险。优先提供原子、可组合、描述清晰的最小能力集。

**误解三：模型足够强就不需要 Harness。** 强模型仍然看不到未提供的状态，也不能绕过真实权限、网络和资源限制。模型能力越强，行动边界和验证通常越重要。

**误解四：自主 Agent 不需要人。** 人需要定义目标、风险和验收方式，并在不可逆或无法验证的节点承担判断责任。自主性改变人的介入位置，不取消人的责任。

**误解五：Workflow 比 Agent 低级。** Workflow 用确定性换来可预测性。生产系统常用 Workflow 固定大结构，让 Agent 只处理其中路径开放的部分。

## 1.13 本课程综合得到的结论

十一个来源的证据地位不同。下面六条是本课程把理论主线、工程主线和案例证据合并后得到的判断，不表示每个来源都逐条提出了相同主张。

1. Agent 必须放在环境中理解。脱离目标、观察和行动谈 Agent，只剩产品标签。
2. 自主性体现为决策权的分配，而且可以按行动风险分级。
3. LLM 把通用语言理解和任务先验带入决策核心，但没有替代规则、状态、搜索和验证。
4. Workflow 与 Agent 的关键差异是路径由代码预定义，还是由模型根据反馈在运行时选择。
5. 大多数应用工程师构建的是 Harness：为模型设计可观察、可行动、可治理、可恢复的工作环境。
6. Agent 的生产难点集中在状态、边界和反馈质量，而不是让最小循环先跑起来。

## 1.14 本章自检

1. 为什么 `Model + Harness` 不能替代智能体的通用定义？
2. 用 PEAS 描述一个“自动整理会议纪要并创建任务”的 Agent。
3. 部分可观察和动态环境分别会引入哪些工程问题？
4. 反射式、目标式和效用式智能体的决策依据有什么差别？
5. LLM 时代为什么仍然需要符号规则和确定性程序？
6. 一个包含多个 LLM 节点的流程为什么仍可能只是 Workflow？
7. 哪些约束可以放进 Prompt，哪些必须由代码执行？
8. 工具与 Harness 内部服务的边界是什么？
9. 为什么自主性更适合被看成连续谱？
10. 设计 Agent 时，为什么应该先定义任务环境再选择框架？

## 1.15 开放性问题

1. 如果系统能自主规划，却只能输出建议、不能改变环境，它在多大程度上算 Agent？你的判断依据是什么？
2. 当模型能力持续增强时，Harness 中哪些能力会变薄，哪些能力反而会变得更重要？
3. 目标和效用由谁定义？当用户短期目标与长期利益冲突时，Agent 应该服从哪一层？
4. 能够通过经验修改 Skill 或记忆的系统，和能够更新模型权重的系统，哪一个更接近“学习型智能体”？
5. 在一个混合系统中，怎样证明某个步骤确实需要 Agent，而不是可以改成更便宜、更稳定的 Workflow？
6. 人把多少决策权交给 Agent，取决于模型能力，还是取决于验证器和损失上限？
